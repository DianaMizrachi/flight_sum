# aura — מערכת תמלול, זיהוי אירועים וסיכום טיסה

מימוש לפי [flight-transcript-work-plan.md](./flight-transcript-work-plan.md).
התמלולים בעברית; ה-LLM קורא ומזהה אירועים בעברית, והסיכומים (רכיב 7/8)
מופקים בעברית.

**מצב נוכחי: שלבים 0-9 הושלמו** - תשתית, חוזים ונתוני בדיקה (שלב 0),
רכיב 1 (קליטת משפטים) עם נרמול, זיהוי כפילויות, dead-letter ותור פנימי
(שלב 1), רכיב 2 (מאגר התמלול הגולמי) - append-only עם שליפה לפי מזהה,
טיסה וטווח זמן (שלב 2), רכיב 3 (בניית הקשר) - חלונות, היסטוריה
רלוונטית ותקציב טוקנים (שלב 3), רכיב 4 (מנוע ה-LLM) - prompt מהטקסונומיה,
פענוח מוגבל-סכמה וניקוד מול תרחישים מתויגים (שלב 4), רכיב 5 (אימות
פלט) - כללים מול הטקסונומיה, בדיקת מזהים, זיהוי סתירות ומדיניות תיקון
(שלב 5), רכיב 6 (מנהל מצב המשימה) - כללי עדכון לפי יחס המידע, ספי
ביטחון, היסטוריה שאינה נמחקת ורשומות ``StateChange`` (שלב 6), רכיב 7
(מאגר אירועים ומצב) - אחסון append-only ושחזור מצב לכל נקודת זמן
(שלב 7), רכיב 8 (תקצירים) - תקציר מוגבל בגודל לפי טריגרים, גרסאות,
ובחירת נקודות ציון (שלב 8), ורכיב 9 (שירות שאילתות) - מצב נוכחי, מצב
בנקודת זמן בעבר, ציר זמן מסונן, ייחוס לתמלול, בחירת גרסה והשוואה בין
גרסאות (שלב 9).

**הצינור המלא 1→8 מחובר** (`src/aura/pipeline.py`): משפט נכנס בקצה אחד,
ומצב משימה, סיכום טיסה ונקודות ציון יוצאים בשני ונשמרים. **רכיב 9 הוא
שכבת הקריאה מעל מה שנשמר** - הוא אינו חלק מהצינור ואינו צריך מודל, ולכן
הוא נבדק מול מסד שנטען מפיקסצ'רים בלבד.

רכיבים 3-9 בנויים ונבדקים אך הם עדיין ספריות - אף נקודת קצה ב-HTTP אינה
קוראת להם, וזה נפתח בשלב 10. שלבים 10-12 עדיין לא הושלמו: שלב 10 חלקי
(ה-API והקליינט חושפים את הקליטה ואת התמלול הגולמי בלבד), ושלבים 11-12
קיימים כשלד ריק (`src/aura/reconciler/`), לפי מבנה הרכיבים בתכנית.

## הרצה מקומית

### התקנה

```bash
unset PYTHONPATH                    # ראו ההערה למטה - נדרש במכונה הזו
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev,api]"         # api נדרש להרצת השרת והדשבורד
```

> הערה לסביבה הזו בלבד: יש משתנה סביבה `PYTHONPATH` גלובלי שמצביע על
> `/usr/lib/python3/dist-packages` ומתנגש עם venv (שובר ייבוא `pydantic`).
> יש להריץ `unset PYTHONPATH` לפני הפעלת ה-venv. זו תכונה של המחשב הזה,
> לא של הפרויקט.

### בדיקות

```bash
pytest                              # 1051 עוברות, 25 מדולגות; ללא רשת וללא GPU
ruff check src tests scripts
```

### לראות את הצינור רץ

רכיבים 3-9 אינם חשופים ב-HTTP עד שלב 10, ולכן אין דרך לראות אותם
בדשבורד. `scripts/run_pipeline.py` הוא החלון אליהם - הוא מריץ טיסה דרך
הרכיבים האמיתיים ומדפיס את האירועים, מצב המשימה, התקציר, נקודות הציון,
ואת התשובות שרכיב 9 מחזיר על מה שנשמר:

```bash
# תגיות ידניות מטיסת זהב דרך רכיבים 5-9. בלי מודל, בלי GPU.
python scripts/run_pipeline.py --tagged flight_01_recon_patrol

# קובץ תמלול דרך כל 1→9, עם תשובת מודל קבועה מראש (בודק השחלה בלבד)
python scripts/run_pipeline.py samples/fixtures/flight_01_recon_patrol.txt

# הדבר האמיתי - דורש ollama מקומי
python scripts/run_pipeline.py --model qwen3:14b samples/fixtures/eval_01_clean_baseline.txt
```

הדוח אומר באיזה מצב הוא רץ, כי ההבדל בין השלושה הוא בדיוק כמה מהמערכת
באמת מופעלת: התגיות הן קלט נכון בוודאות, המודל המדומה מוכיח חיווט
ולא איכות, והמודל האמיתי הוא היחיד שבודק זיהוי אירועים.

הבדיקות מריצות מודל מדומה בלבד. אין צורך ב-ollama, ב-docker או ב-GPU.

### השירות והדשבורד

```bash
uvicorn aura.api:app --reload
```

| כתובת | מה יש שם |
| --- | --- |
| <http://localhost:8000/> | **הקליינט** - הזנת משפטים וצפייה בתמלול |
| <http://localhost:8000/ops> | מצב המערכת (תצוגת פיתוח) |
| <http://localhost:8000/docs> | Swagger |
| <http://localhost:8000/redoc> | ReDoc |
| <http://localhost:8000/status> | מצב המערכת כ-JSON |

`:memory:` נותן הרצה חולפת:

```bash
AURA_RAW_STORE_PATH=:memory: uvicorn aura.api:app
```

### תשתית אופציונלית

`docker-compose.yml` מרים Postgres ו-Redis בלבד. אין בו שירות LLM
בכוונה - ראו ההערה בקובץ. שום דבר ממה שרץ כאן כרגע אינו תלוי בו:
המאגר הוא SQLite והתור הוא בזיכרון עד שיוחלפו בשלבים מתקדמים.

## רכיב 1 — קליטת משפטים (שלב 1)

```python
from aura.ingestion import IngestionService

service = IngestionService()
result = service.ingest({
    "id": "flight-01-m01",         # אם חסר - נגזר מה-hash
    "flight_id": "flight-01",
    "timestamp": "2026-09-01T06:00:00Z",
    "source": "operator",
    "channel": "command",
    "text": "בקרה, נץ אחת, הכל תקין.",
})
result.status        # accepted / duplicate / dead_letter
result.message       # Message מנורמל (קיים גם לכפילות, מסומן כ-duplicate)
service.queue.drain()    # ההודעות שהועברו לעיבוד אסינכרוני
service.dead_letters     # הודעות פגומות, עם סיבה והמקור הגולמי
```

| כלל | התנהגות |
| --- | --- |
| נרמול | NFC, הסרת תווי כיווניות/אפס-רוחב, כיווץ רווחים, זמן ל-UTC |
| שמירת המקור | טקסט שעבר נרמול נשמר במקביל ב-`metadata["raw_text"]` |
| כפילות | לפי `id` מהמקור; בהיעדרו לפי hash של טיסה+מקור+זמן+טקסט |
| הודעה פגומה | dead-letter עם `reason` (`missing_required_field`, `empty_text`, `invalid_timestamp`, `schema_invalid`) |
| הודעה באיחור | `timestamp` המקורי נשמר כפי שהוא; `ingested_at` מתעד את זמן הקליטה |

שני דברים נדחו במכוון לשלב שבו יהיה להם צורכן: התור (`MessageQueue`)
והאינדקס (`DedupIndex`) מוגדרים כ-Protocol עם מימוש בזיכרון בלבד - מימוש
מעל Redis ומעל מאגר התמלול הגולמי נכנס בשלבים 2-3, כשיהיה מי שקורא מהתור
ומי שמזהה כפילות אחרי אתחול באמצע טיסה.

## רכיב 2 — מאגר התמלול הגולמי (שלב 2)

```python
from aura.ingestion import IngestionService
from aura.raw_store import RawStoreDedupIndex, SQLiteRawTranscriptStore

store = SQLiteRawTranscriptStore("var/aura-raw.db")        # ":memory:" לבדיקות
service = IngestionService(store=store, dedup_index=RawStoreDedupIndex(store))
service.ingest({...})                      # נכתב למאגר *לפני* שהועבר לתור

store.get("m04", flight_id="flight-01")    # שליפה לפי המפתח (טיסה + מזהה)
store.get("flight-01-m04")                 # בלי טיסה - רק אם המזהה חד-משמעי
store.by_flight("flight-01")               # כל הטיסה, בסדר כרונולוגי
store.by_time_range("flight-01", start, end)   # טווח זמן בתוך טיסה (כולל גבולות)
store.flights(); store.count("flight-01")
```

| כלל | התנהגות |
| --- | --- |
| append-only | אין `update` ואין `delete` ב-API, **והמנוע עצמו חוסם אותם** |
| סדר כרונולוגי | מיון לפי ה-`timestamp` המקורי, כך שהודעה באיחור חוזרת למקומה |
| טקסט | נשמר ונשלף זהה בייט-בייט; הנוסח שלפני הנרמול נשאר ב-`metadata["raw_text"]` |
| מפתח | `(flight_id, id)` - המזהה בא מהמקור וייחודי בתוך הטיסה שלו, לא במאגר |
| כפילות | כתיבת מזהה שקיים *באותה טיסה* מעלה `DuplicateMessageError`; `append_many` היא הכול-או-כלום |
| הודעה פגומה | אינה נכתבת למאגר - היא אינה `Message` תקין; המקור הגולמי נשמר ברשומת ה-dead-letter |

**המזהה הוא של המקור, ולכן ייחודי בתוך הטיסה.** שתי טיסות יכולות שתיהן
למנות את שורותיהן `m01` - וזה המצב הרגיל, לא התנגשות. המפתח הראשי הוא
`(flight_id, id)`, ו-`get`/`exists` מקבלים `flight_id` כדי לשלוף לפיו.
מזהה בלי טיסה אינו מפתח: הוא נשלף כל עוד הוא חד-משמעי, ואם הוא קיים
בכמה טיסות מתקבל `AmbiguousMessageIdError` (ב-HTTP: 409 עם רשימת
הטיסות) ולא שורה שרירותית. חזרה מאירוע לתמלול תמיד מעבירה את שני
השדות, כי `Event` מחזיק את שניהם.

עד התיקון המפתח היה `id` לבדו. התוצאה הייתה שגיאה שקטה בשני קצוות:
רכיב 1 אישר את ההודעה (מפתח הכפילות שלו משויך לטיסה), המאגר דחה אותה על
התנגשות מזהה, והקליטה החזירה `duplicate` על הודעה שאין במאגר אף אחת
כמותה. מאגר שנוצר לפני התיקון עובר למפתח החדש בפתיחה הראשונה
(`sqlite_store.py`, ו-`migrations/002` ל-Postgres): הטבלה הישנה מועברת
הצידה, השורות מועתקות כפי שהן, ורק אחרי אימות שלא נשארה שורה מאחור היא
נמחקת - כך שהפסקה באמצע ממשיכה בפתיחה הבאה.

**חסימת עדכון ומחיקה "לא רק בקוד".** ב-SQLite האכיפה היא בטריגרים
(`schema.sql`), כך שגם SQL ישר נדחה:

```python
store.execute_sql("UPDATE raw_messages SET text = 'שונה' WHERE id = 'flight-01-m04'")
# AppendOnlyViolationError: raw_messages is append-only: UPDATE is blocked
```

ב-Postgres (היעד ב-docker-compose) האכיפה היא בהרשאות + טריגר:

```bash
docker compose exec -T postgres psql -U aura -d aura \
  < src/aura/raw_store/migrations/001_raw_messages.postgres.sql
docker compose exec -T postgres psql -U aura -d aura \
  < src/aura/raw_store/migrations/002_flight_scoped_message_id.postgres.sql
```

הטבלה נוצרת בבעלות role של מיגרציות, והשירות מתחבר ב-role שמקבל
`SELECT, INSERT` בלבד - ב-Postgres בעל טבלה שומר תמיד את הרשאותיו, ולכן
`REVOKE` ממנו אינו מספק. המיגרציה עצמה אינה מורצת ב-CI (אין שם מסד); מה
שנבדק אוטומטית הוא מימוש ה-SQLite, שבו רצות כל בדיקות השלב.

**האינדקס הנמשך לזיהוי כפילויות.** `RawStoreDedupIndex` מחליף את האינדקס
בזיכרון של שלב 1, ולכן שירות שעלה מחדש באמצע טיסה עוד מזהה הודעה שכבר
נקלטה (נבדק ב-`test_raw_store.py`, וגם מול שרת חי).

מה שעוד לא: הכתיבה למאגר נעשית סינכרונית בתוך הקליטה. הקריאה מהתור
(עיבוד אסינכרוני בפועל) נכנסת בשלב 3 עם בניית ההקשר.

## רכיב 3 — בניית הקשר (שלב 3)

```python
from aura.context_builder import ContextBuilder, InMemoryEventHistory, assemble_windows

windows = assemble_windows(store.by_flight("flight-01"))   # חלוקה לחלונות
builder = ContextBuilder(history=InMemoryEventHistory(known_events))
bundle = builder.build(windows[0], current_state=state, last_summary=summary)

bundle.messages              # החלון, כולל החפיפה מהחלון הקודם
bundle.relevant_history      # רק אירועי הישויות שמוזכרות בחלון
bundle.token_budget          # budget / used_estimate / history_items_dropped
```

זרימת זמן אמת, מול זרימת סוף טיסה:

| מצב | כלי | התנהגות בהודעה שמגיעה באיחור |
| --- | --- | --- |
| זמן אמת | `WindowAssembler.push()` / `QueueWindowPump` | אם החלון שלה נסגר - נרשמת ב-`orphans` ולא נדחפת לחלון לא נכון |
| סוף טיסה / שלב 11 | `assemble_windows()` | ממוין לפי החותמת המקורית לפני החלוקה, ולכן אין יתומים |

שלוש החלטות תכן שהתכנית משאירה פתוחות, ומסומנות ב-`config.py`:

- **`max_sentences` כולל את החפיפה** (ה-LLM רואה אותה), אבל
  **`max_duration_seconds` נמדד על משפטי החלון עצמו** - אחרת שתיקה ארוכה
  שנגררה מהחלון הקודם הייתה סוגרת מיד את החלון החדש.
- **הודעה באיחור אינה נדחפת לחלון הפתוח** (`include_late_messages=False`):
  עדיף לרשום אותה כיתומה ולתת למעבר התיקון של שלב 11 לטפל בה, מאשר
  לשבש את סדר המשפטים בזמן אמת.
- **התאמת הישויות מתעלמת ממילה שמשותפת לכמה תוויות**: "מטרה" מופיעה
  בתווית של כל מטרה ולכן אינה מזהה אף אחת מהן, בעוד "אלפא" מזהה. בלי
  הכלל הזה חלון שמזכיר את אלפא היה גורר גם את ההיסטוריה של בטא.

### מה שהמדידה מראה על ספי החלון

החלוקה לחלונות רצה על שלוש טיסות הזהב ועל `samples/flight_sim_01.txt`
(62 משפטים בסך הכול), בכמה הגדרות:

| `silence` | `max_duration` | סגירה בהחלפת דובר | חלונות | משפטים לחלון | טוקנים מרביים |
| --- | --- | --- | --- | --- | --- |
| **20 (ברירת המחדל)** | **90** | **כן** | **61** | **1.0** | 447 |
| 20 | 90 | לא | 50 | 1.2 | 502 |
| 60 | 180 | לא | 40 | 1.6 | 502 |
| 180 | 600 | לא | 27 | 2.3 | 654 |

שתי מסקנות:

1. **בברירת המחדל כל חלון הוא משפט אחד.** הרכיב עומד בדיוק בכללים
   שבתכנית, אבל בתעבורת קשר אמיתית התוצאה היא קריאת LLM לכל משפט - בדיוק
   מה שהמעבר לחלונות נועד לחסוך. הגורם הדומיננטי הוא סף השתיקה
   (46 מתוך 61 הסגירות), לא החלפת הדובר.
2. **תקציב הטוקנים אינו האילוץ.** גם בהגדרה הרחבה ביותר חבילה אחת מגיעה
   ל-654 טוקנים מתוך 4000, כך שה-PLACEHOLDER של 4000 מרווח - והאילוץ
   האמיתי הוא מספר המשפטים והזמן, לא התקציב.

ההמלצה: `silence_threshold_seconds=60`, `max_duration_seconds=180`,
`close_on_speaker_change=False` - אלו מקבצים חילוף דברים שלם לחלון אחד
במקום משפט בודד. הערה חשובה: טיסות הזהב דלילות (12-14 משפטים לטיסה),
ושאלת "נפח ההודעות הצפוי לטיסה" פתוחה בתכנית - כשיהיו נתונים אמיתיים
כדאי להריץ את המדידה הזו שוב. ברירות המחדל בקוד נשארו **כמו בתכנית**
עד להחלטה.

## הקליינט - הזנת תמלול

```bash
uvicorn aura.api:app --reload      # ואז http://localhost:8000/
```

שני דפים, לשני קוראים שונים - וההפרדה הזאת מכוונת:

**`/` - הקליינט.** הדף של מי שמזין תמלול. טופס שדה-אחר-שדה (טיסה, דובר,
ערוץ, זמן, המשפט), ולידו התמלול המצטבר של אותה טיסה. אין בו שלבי תכנית
עבודה, טבלת רכיבים או תקציבי טוקנים - אין להם מה לעשות על המסך של מי
שמתעד שיחת קשר. בדיקה (`test_root_is_the_client_and_not_the_ops_dashboard`)
נכשלת אם מידע פיתוח חוזר ומחלחל לדף הזה.

מה שהטופס עושה כדי שהזנה רצופה תהיה מהירה: מזהה הטיסה, הדובר והערוץ
נזכרים בין משפטים, חותמת הזמן מתקדמת ל"עכשיו" אחרי כל שליחה, רק תיבת
הטקסט מתרוקנת, והמיקוד חוזר אליה. `Ctrl+Enter` שולח.

התוצאה מוצגת מיד בשפת המשתמש ולא כקוד HTTP: *נקלט* (עם המזהה, ואם הטקסט
נורמל - גם הנוסח שנשמר), *כפילות*, או *נדחה* עם הסיבה בעברית. הודעה
שנדחתה נשארת בתמלול שבמסך עם קו חוצה, כי היא אינה נכנסת למאגר ואי אפשר
לשלוף אותה אחרי רענון. שלושת המונים שמעל התמלול - נקלטו, כפילויות,
נדחו - הם של הטיסה שבמסך; "נקלטו" מגיע מהמאגר, ושני האחרים הם של הסשן,
כי כפילות ודחייה אינן הודעה שאפשר לשלוף בחזרה.

**התחלת טיסה מחדש.** לצד שדה מזהה הטיסה יש כפתור "התחל מחדש", למי
שרוצה להריץ את אותה טיסה שוב מאפס - תרגיל נוסף, קובץ תמלול מתוקן, או
סתם מסך נקי. המאגר הוא append-only, ולכן אין כאן מחיקה: הכפתור פותח
*ריצה חדשה במזהה חדש* (`flight-01` ← `flight-01-run2`, וכן הלאה; מזהה
שכבר תפוס מדלג לריצה הבאה הפנויה). התמלול והמונים שבמסך מתאפסים, הטיסה
הקודמת נשארת שלמה ונשלפת לפי המזהה שלה, ואותו קובץ תמלול אפשר להזרים
שוב מבלי שייחשב כפילות. שורות שהמתינו להשלמה שייכות לריצה שהסתיימה,
ולכן הן נוקו - והדף אומר כמה, כדי שלא ייעלמו בשקט.

**השלמת שורות חסרות.** הודעה שנדחתה - בין אם הוזנה בטופס ובין אם הגיעה
מקובץ - נכנסת לטבלה "שורות שצריכות השלמה". כל שורה מוצגת עם מה שכן היה
בה, השדות החסרים מסומנים בצהוב, וניתן למלא ולשלוח. יש גם השלמה קבוצתית
לשדה אחד בכל השורות שבהן הוא חסר (למשל קובץ שבכולו אין `source`), והיא
ממלאה רק את החסר ואינה דורסת ערך שהגיע מהקובץ. שורה שנשלחה חסרה עדיין
נדחית, והסיבה מוצגת בשורה עצמה.

זה חוסך את המסלול של "תקן את הקובץ והעלה הכול מחדש", שגם היה מייצר
כפילויות על כל מה שכבר נקלט. השורה נשלחת עם המזהה המקורי שלה, ולכן
היא נקלטת במקומה הכרונולוגי.

הטבלה חיה בדף בלבד: הודעה שנדחתה אינה נכנסת למאגר הגולמי, ולכן רענון
הדף מאבד את הרשימה. הסיבה והנתון הגולמי נשמרים בלוג הדחיות
(`GET /dead-letters`), אבל ההשלמה היא פעולה של המשתמש ולא מצב של השרת.

**`/ops` - מצב המערכת.** תצוגת הפיתוח: אילו שלבים נבנו, אילו רכיבים
חשופים ב-API, כמה משפטים וטיסות במאגר, מה בתור, אילו הודעות נדחו ולמה,
האם ollama זמין ואיזה מודל מותקן בו בפועל, ומה ספי החלון שבתוקף.
מתרענן כל 5 שניות כברירת מחדל.

#### מה התמלול מראה

בראש התמלול נכתב מזהה הטיסה שכל השורות שייכות אליה, וליד כל משפט נכתב
מזהה ההודעה שלו. המזהה הוא המפתח שבו מדברים על המשפט בכל מקום אחר
במערכת - שליפה לפי מזהה, `source_ids` של אירוע, ודיווח על כפילות - ולכן
הוא נראה בדף ולא רק קיים בנתונים. שורה שנקלטה בלי מזהה מהמקור מציגה את
המזהה שנגזר לה מ-hash; שורה שנדחתה ואין לה מזהה כלל אומרת זאת במפורש
במקום להציג שדה ריק.

### העלאת תמלול מהמחשב

בראש הקליינט, מעל טופס ההזנה, יש פס להעלאת קובץ תמלול שלם - למי שמזין
טיסה שהוקלדה מראש ולא משפט-משפט. אפשר לגרור קובץ לכל מקום בדף (הפס
מודגש כדי שיהיה ברור לאן הוא הולך) או לבחור אותו בכפתור. התוצאה מוצגת
מיד: כמה נקלטו, כמה כפילויות, והשורות שנדחו עם **מספר השורה בקובץ**
והסיבה.

הפורמט הוא זה שמתועד ב-`samples/flight_sim_01.txt`:

```
message_id | timestamp | source | channel | text
```

שורות `#` וריקות הן הערות. מזהה הטיסה אינו שדה בשורה אלא תכונה של
הקובץ: הוא נלקח מהנחיית `# flight_id: <id>` שבקובץ, או מהשדה בטופס -
והשדה גובר. בלי אף אחד מהם הקובץ נדחה כולו ב-400, כדי שלא ייקלטו 29
הודעות שכולן חסרות את אותו שדה.

אותו קובץ אפשר להזרים שוב כטיסה אחרת: `message_id` שבשורה הוא של המקור,
והוא ייחודי *בתוך הטיסה* - כך שהקלדת מזהה טיסה חדש בשדה "מזהה טיסה"
קולטת מחדש את כל השורות. אותו קובץ לאותה טיסה הוא כפילות, וזה בכוונה.
(המפתח במאגר היה פעם `id` לבדו, ואז הטיסה השנייה חזרה כולה כ-`duplicate`
למרות שאין במאגר אף הודעה שלה; ראו "מאגר התמלול הגולמי" למטה.)

אותו דבר משורת הפקודה:

```bash
curl -X POST -F "file=@samples/flight_sim_01.txt" http://localhost:8000/messages/upload
```

#### הפיקסצ'רים המתוייגים כקבצים להעלאה

`samples/fixtures/` מחזיק את כל פיקסצ'ר תגיות שבפרויקט כקובץ `.txt`
בפורמט שלמעלה - שלוש טיסות הזהב, שלושת תרחישי השוואת המודלים וארבעת
מקרי הגבול. עד כה המשפטים האלה היו קיימים רק כ-YAML שבדיקה קוראת, ולכן
הקובץ היחיד שאפשר היה להעלות בדשבורד היה `samples/flight_sim_01.txt`.

שני הקבצים עובדים: אפשר להעלות את ה-`.txt` מ-`samples/fixtures/`, או את
פיקסצ'ר ה-`.yaml` עצמו מ-`tests/fixtures/` - ההעלאה מזהה את הפורמט לפי
תוכן הקובץ. שניהם נקלטים דרך אותו רכיב 1, ושתי צורות של אותו פיקסצ'ר
נותנות את אותם משפטים תחת אותם מזהים (`tests/test_fixture_yaml_upload.py`).

כל קובץ נושא הנחיית `# flight_id:` משלו, ולכן אין צורך להקליד מזהה
טיסה; בראשו כתוב מאיזה פיקסצ'ר הוא נוצר ומה ההעלאה אמורה להחזיר
(`x נקלטות, y כפילויות, z ל-dead-letter`), והמספרים נמדדים בזמן היצירה
על ידי קליטה אמיתית ולא נכתבים ביד.

הקבצים נוצרים מהפיקסצ'רים ולא נערכים ישירות:

```bash
python scripts/export_fixture_transcripts.py            # כתיבה מחדש
python scripts/export_fixture_transcripts.py --check    # בדיקת היסט
```

`tests/test_fixture_samples.py` מעלה כל אחד מהם דרך
`POST /messages/upload` האמיתי, קורא את התמלול חזרה מ-
`GET /flights/{id}/messages` - אותו מקום שממנו הקליינט קורא - ומשווה כל
משפט לתג שבפיקסצ'ר. היא גם נכשלת אם קובץ התיישן מול הפיקסצ'ר שלו, באותה
רוח שבה הספק ב-`docs/openapi.json` נשמר מסונכרן.

#### שני פורמטים, מסלול קליטה אחד

`POST /messages/upload` מקבל שני פורמטים ומכריע ביניהם לפי תוכן הקובץ
(הסיומת היא רמז בלבד - דפדפן לא תמיד שולח אותה):

| הקובץ | הקורא | מזהה הטיסה |
| --- | --- | --- |
| `.txt` בפורמט הצינורות | `ingestion/text_format.py` | הנחיית `# flight_id:` |
| פיקסצ'ר `.yaml` | `ingestion/fixture_transcripts.py` | השדה `flight_id:` |

מכאן והלאה אין שני מסלולים: אותו רכיב 1, אותו נרמול, אותו זיהוי
כפילויות ואותו dead-letter. שדה "מזהה טיסה" בטופס גובר על שני המקורות.

הפיקסצ'ר נקרא דרך אותו מודול שממנו נוצרים קבצי `samples/fixtures/`, ולכן
אין הגדרה שנייה של "המשפטים שבפיקסצ'ר הזה". הודעה בפיקסצ'ר פרושה על כמה
שורות קובץ, ולכן היא מקבלת `metadata.source_index` (המקום ברצף) במקום
`metadata.source_line` - מספר שורה היה צריך להיות מומצא שם.

בנקודה אחת העלאת הפיקסצ'ר מדויקת *יותר* מקובץ הצינורות: ב-`.txt` מזהה
הטיסה הוא שדה של הקובץ כולו, ולכן השורה של `malformed_and_empty` שנשלחה
בלי `flight_id` נקלטת ומתקבלות 4 דחיות; בפיקסצ'ר היא נשארת בלי מזהה
טיסה ומתקבלות 5 - בדיוק מה שהפיקסצ'ר מצהיר עליו.

קובץ שאינו אף אחד מהשניים - אף שורה בלי חמשת השדות, ובלי מפתח הודעות
מוכר - נדחה כולו ב-400 (`not a transcript`) ולא נקלט שורה-שורה, אחרת
כל שורה בו הייתה מגיעה ל-dead-letter בנפרד והמשתמש היה מקבל מאות שורות
"להשלמה" במקום לדעת שבחר את הקובץ הלא נכון. שורה תקינה אחת מספיקה כדי
שהקובץ ייחשב תמלול, ואז השורות הפגומות שבו מגיעות ל-dead-letter עם סיבה
כרגיל - "שמירה לפני עיבוד" נשאר בתוקף.

שני דברים שפורמט הקובץ אינו יכול לשאת, ומתועדים בבדיקה בשמם ולא
מתעגלים: שורה שנגמרת אחרי הערוץ נותנת טקסט *ריק* ולא "שדה חסר", כי
פורמט שורה-אחת-להודעה אינו מבדיל ביניהם; ומזהה הטיסה הוא שדה של הקובץ
כולו, ולכן שורה שבפיקסצ'ר נשלחה בלי `flight_id` נקלטת בהעלאה במקום
להידחות. לכן `malformed_and_empty.txt` מחזיר 4 דחיות ולא 5.

הקורא (`ingestion/text_format.py`) מקפיד על המבנה ומקל על התוכן: שורה
בלי חותמת זמן או בלי טקסט נשלחת לקליטה בכל זאת ומגיעה ל-dead-letter עם
סיבה, במקום להיעלם בקורא. זה מה ששומר על לוג ה-dead-letter כמקום היחיד
לחפש בו הודעה שלא נכנסה. שתי נקודות שבהן המימוש המובן-מאליו מאבד מידע:
הטקסט נחתך ב-`maxsplit=4` כדי שמשפט שמכיל `|` יישמר, והריווח *בתוך*
המשפט נשמר כי הנרמול הוא תפקידו של רכיב 1.

כל הודעה שנקלטת מקובץ מקבלת `metadata.source_file` ו-`metadata.source_line`,
כך שאירוע שיזוהה בהמשך ניתן לייחוס לא רק למשפט אלא לשורה שממנה נקלט.
קובץ שאינו UTF-8 נדחה במפורש ולא מנוחש - עברית ב-cp1255 הייתה מתפענחת
לג'יבריש סביר למראה במקום להיכשל.

הנתונים באים מ-`GET /status`, והדף הוא HTML+JS ללא תלויות וללא שלב בנייה
(`src/aura/api/static/index.html`), מוגש מהשירות עצמו.

שתי הבחנות שהדף שומר במפורש, כי בלעדיהן דף מצב מציג תמונה אופטימית
מהמצב בפועל:

- **"נבנה" מול "חשוף ב-API".** רכיבים 3-8 ממומשים ונבדקים, והצינור
  המלא 1→8 רץ (`aura.pipeline`) ומפיק סיכום ונקודות ציון - אבל בתוך
  התהליך בלבד. אף נקודת קצה
  ב-HTTP אינה קוראת להם; זה נפתח בשלב 10.
- **מודל מוגדר מול מודל מותקן.** `LLMConfig.model` הוא מחרוזת בקובץ
  הגדרות; הדף שואל את ollama מה באמת מותקן ומה טעון בזיכרון, ומסמן
  באדום מודל מוגדר שאינו קיים.

ollama שלא נגיש אינו מפיל את הדף - זה מידע, לא תקלה. הזמן קצוב ל-2 שניות.

## רכיב 4 — מנוע ה-LLM (שלב 4)

חלון משפטים נכנס, ``LLMResult`` יוצא. ארבעה חלקים:

| קובץ | תפקיד |
| --- | --- |
| `prompt.py` | prompt בעברית שנבנה מהטקסונומיה. הוספת סוג אירוע ל-`event_types.yaml` משנה את ה-prompt בלי שינוי קוד. |
| `client.py` | `LLMClient` כ-Protocol, `OllamaClient` אמיתי, `MockLLMClient` לבדיקות, ו-`RecordingLLMClient` שמייצר fixtures מתשובות אמיתיות. |
| `engine.py` | מריץ, מפענח ומאמת סכמה. `window_id`, `llm_model` ו-`raw_response` בבעלות המנוע ולא בבעלות המודל. |
| `scoring.py` | חמישה מדדים נפרדים: זיהוי, ייחוס מקורות, פיצול, מלכודות וסוג שגוי. |

**הסכמה שנשלחת למודל צרה מ-`LLMResult` בכוונה.** `LLMResult` כולל
`llm_model` ו-`raw_response`, שהם מטא-דאטה של ההרצה. בפענוח מוגבל-סכמה
מודל *חייב* למלא כל שדה בסכמה, כלומר היה נאלץ לנחש את שמו של עצמו -
ולכן המודל מוגבל ל-`ModelEventsResponse` (רשימת אירועים בלבד) והמנוע
עוטף את התוצאה.

**הפענוח המוגבל הוא גם הסיבה שקריטריון ה-98% אינו מדד שמבדיל בין
מודלים.** `format` של ollama מקבל סכמת JSON מלאה, ולכן JSON פגום אינו
אפשרי לשום מודל. המדד שבאמת מבדיל הוא ייחוס המקורות (90%).

### שני פרופילי prompt, כמדידה ולא כהעדפה

`MINIMAL` מגדיר את המשימה, הקטלוג ומבנה הפלט. `GUARDED` מוסיף שבעה
כללים: ציטוט מקור, אישורים שאינם אירוע, שאלות, שלילה, הוראות מותנות,
דיווחי שגרה, ו"אל תמציא". ההרצה בשני הפרופילים מפרידה בין "המודל לא
הבין את העברית" לבין "המודל לא יישם כלל שנאמר לו במפורש" - שתי תקלות
שהתיקון שלהן שונה לגמרי. בפועל: 796 טוקנים ב-`MINIMAL` מול 1,120
ב-`GUARDED`, מול `num_ctx` של 8,192.

### הרצת ההשוואה

ollama רץ על המארח (לא בקומפוז - ראו ההערה ב-`docker-compose.yml`):

```bash
ollama pull hf.co/dicta-il/DictaLM-3.0-Nemotron-12B-Instruct-GGUF:Q4_K_M

python scripts/evaluate_llm.py \
    --model hf.co/dicta-il/DictaLM-3.0-Nemotron-12B-Instruct-GGUF:Q4_K_M \
    --model qwen3.6:27b \
    --profile minimal --profile guarded
```

הסקריפט מריץ גם את סט הזהב (`--suite golden`) לקו הבסיס של
Precision/Recall, ו-`--record DIR` שומר כל תשובה אמיתית כ-fixture.
ברירת המחדל של החלונות בסקריפט היא התצורה המומלצת ולא זו של התכנית,
כי בתצורת התכנית כל משפט הוא חלון נפרד - ואז המודל רואה אישור בלי
הדיווח שהוא מאשר, כך שמלכודת הספירה הכפולה הופכת לארטיפקט של החלונות
במקום למדידה של המודל. `--plan-defaults` מודד בדיוק את ההפרש הזה.

## רכיב 5 — אימות ופענוח פלט (שלב 5)

`LLMResult` נכנס, `ValidatedResult` יוצא: רק אירועים שעומדים בחוזה
ממשיכים הלאה, והשאר נשמרים עם סיבה ועם הפלט הגולמי. קריטריון המעבר של
השלב הוא שלילי - *שום פלט פגום לא מגיע לעדכון המצב* - ולכן הוולידטור
לעולם אינו מתקן אירוע, אינו ממלא שדה חסר ואינו בוחר בין שתי טענות
סותרות. אירוע עומד בחוזה או חוזר לשולח.

### מה נבדק, ולמה כל כלל קיים

| קוד דחייה | מה נתפס |
| --- | --- |
| `not_json` · `schema_invalid` | הפלט אינו בר-פענוח כלל |
| `unknown_event_type` | סוג שאינו בטקסונומיה |
| `missing_required_field` | שדה ש*הסוג* דורש והגיע ריק |
| `entity_type_not_applicable` | ישות מסוג שהאירוע אינו חל עליו |
| `unknown_entity_id` | מזהה ישות שהומצא |
| `source_id_not_in_window` | ייחוס למשפט שלא היה בחלון |
| `contradicting_events_same_source_sentence` | משפט אחד, שתי טענות שאינן יכולות להתקיים יחד |

שום כלל אינו מחזיק ידע תחומי משלו. אילו סוגים קיימים, על אילו ישויות כל
אחד חל, אילו שדות הוא דורש ומה סותר מה - הכול מגיע מהטקסונומיה. לשם כך
נוסף לה השדה `contradicts`: "קשר עם מטרה" ו"אובדן קשר" מוצהרים כסותרים
*שם*, ולא מקודדים בוולידטור, כי מי שמחזיק את הידע הזה לא כותב פייתון.

שלושה גבולות שנקבעו במפורש, כי כל אחד מהם היה יכול להיות גם ההפך:

- **סתירה דורשת שלושה תנאים יחד**: משפט מקור חופף, אותה ישות, וסוגים
  שהטקסונומיה מצהירה כסותרים. פחות מכך היה פוסל מידע תקין - שני אירועים
  שונים מאותו משפט הם דבר רגיל, ושני דיווחים סותרים *על פני זמן* הם כל
  העניין של `relation_to_previous: contradicts`.
- **שני הצדדים של סתירה נדחים, לא אחד.** שום דבר בפלט לא אומר איזה
  מהשניים נכון, ובחירה שרירותית הייתה מעבירה הלאה טענה שאין לה הצדקה.
- **מזהי ישויות נבדקים רק כשיש מול מה לבדוק.** כל עוד רכיב 6 אינו קיים,
  חבילת הקשר עשויה להגיע בלי `current_state`; לדחות אז כל ישות מזוהה
  היה הופך את הוולידטור לחוסם, ולהעמיד פנים שהמזהה נבדק - גרוע מכך.

### מדיניות התיקון

הזדמנות אחת, ולא יותר. הדחיות מנוסחות להודעה שחוזרת למודל, ואם גם
התשובה השנייה נדחית - התוצאה מסומנת `manual_review` וממשיכה הלאה עם
הפלט הגולמי שמור. החסם הוא העיקר: רכיב שנועד להגן על הצינור לא יכול
להיות זה שתוקע אותו.

```python
outcome = validate_with_repair(validator, bundle, detect)
outcome.result.status      # ok / retried / manual_review
outcome.attempts           # 1 או 2
```

### מה שהאימות מצא בפלט אמיתי

הכללים רצים גם על התשובות המוקלטות ב-`tests/fixtures/llm_responses/` -

הראשונה היא פלט חסר, בלי ספק. השנייה היא **החלטה תחומית פתוחה**: אם קשר

## רכיב 6 — מנהל מצב המשימה (שלב 6)

אירועים מאומתים נכנסים, מצב משימה מעודכן יוצא, ולצדו רשומת
`StateChange` לכל שינוי. זהו הרכיב הראשון שהפלט שלו הוא *דעה*: כל מה
שלפניו מעביר מידע בלי לשפוט אותו, וכאן המערכת אומרת לראשונה "זה מה
שנכון עכשיו" - ולכן כל כלל כאן קיים כדי שהיא תוכל להסביר מניין היא
יודעת.

ארבע החלטות שמעצבות את הרכיב:

- **`relation_to_previous` מניע את העדכון, לא סוג האירוע.** המודל כבר
  אמר אם זה מידע חדש, מחליף, סותר או סוגר; לגזור את זה מחדש מהסוג היה
  לתת תשובה שנייה וגרועה יותר לשאלה שכבר נענתה.
- **שום דבר אינו נמחק.** ערך שהוחלף עובר ל-`history` עם האירוע שהביא
  אותו, ולכן "איך הגענו להאמין בזה" תמיד ניתן לענייה. מאותה סיבה
  `contradicted` הוא דגל על המאפיין ולא מחיקה.
- **ביטחון קובע שני דברים נפרדים**: מה המידע *הוא*
  (מאומת / מדווח / לא ודאי), ובנפרד - האם מותר לו לדחוק את מה שכבר שם.
  ניחוש אינו דורס מידע מאומת רק מפני שהגיע אחריו.
- **הזמן מגיע מהמשפט, לא מהשעון.** הודעה שאחרה נושאת חותמת ישנה, וחותמת
  ישנה אינה דוחקת אמונה חדשה יותר: ההודעה חדשה *לנו*, מה שהיא מתארת לא.

סדר העיבוד הוא סדר משפטי המקור. שני אירועים מאותו חלון - "הקשר אבד"
ו"הקשר חודש" - חייבים להיקרא בסדר שנאמרו, אחרת המצב הסופי הוא ההפך
מהאמת. זה התרחיש שהתכנית מדגישה, והוא נבדק גם כשהשניים מגיעים בסדר הפוך.

### שם המאפיין מגיע מהטקסונומיה

ל-`Event` אין שדה מאפיינים: יש לו סוג, `new_info` חופשי והפניות ישות.
לכן הטקסונומיה מצהירה לכל סוג על `state_attribute` - המאפיין שהוא מדבר
עליו - ומנהל המצב כותב את `new_info` תחת השם הזה.

| סוג אירוע | מאפיין |
| --- | --- |
| `contact_with_target` · `loss_of_contact` | `contact_status` |
| `mission_change` | `mission` |
| `malfunction` | `malfunction_status` |

ששני הראשונים חולקים מאפיין אחד הוא כל העניין: "הקשר חודש" מחליף את
"הקשר אבד" במקום לשבת לידו. אילו כל סוג היה כותב למאפיין משלו, המצב היה
מחזיק בו-זמנית "יש קשר" ו"אין קשר", שניהם נוכחיים ושניהם נכונים לעצמם.

### פער ידוע מול נקודות הביקורת של שלב 0

נקודות הביקורת בטיסות הזהב מצפות למאפיינים חילוציים -
`location: "צומת צפוני"`, `fuel_status: "40%..."` - אבל **חוזה
ה-`Event` אינו יכול לשאת אותם**: אין בו שדה מאפיינים כלל. זהו פער אמיתי
בין הפיקסצ'רים של שלב 0 לחוזים של שלב 0, ולא באג ברכיב 6.

מה כן מושווה, ועובר במלואו בשלוש טיסות הזהב: אותן **ישויות**, אותם
סוגים, אותן תוויות ואותו סטטוס פתוח/סגור. מזהי הישויות אינם מושווים -
הפיקסצ'רים משתמשים בתעתיק שנבחר ביד (`target-alpha`), שאין כלל שיגזור
אותו מ-"מטרה אלפא"; הרכיב גוזר מזהה יציב משלו
(`target-mtrh-alpa`) וההשוואה היא לפי סוג+תווית.

לסגור את הפער פירושו שינוי חוזה - שדה `attributes` ב-`LLMEvent`, ועדכון
ה-prompt של שלב 4 בעקבותיו - ולכן זו החלטה ולא תיקון.
`test_state_manager_golden.py` מחזיק בדיקה שנכשלת *כשהפער ייסגר*, כדי
שאז יוסר התיעוד הזה ויושוו גם ערכי המאפיינים.

### הצינור המלא 1→6

`src/aura/pipeline.py` הוא החוט בין הרכיבים, והתכנית מסמנת את הרגע שבו
הוא קיים כנקודת הביקורת המרכזית של הפרויקט:

```python
pipeline = FlightPipeline(ingestion, engine)
pipeline.ingest({...})          # רכיב 1 — זהה ל-POST /messages
pipeline.drain()                # 3→4→5→6 לכל חלון שנסגר
pipeline.close_flight("f1")     # סוף טיסה
pipeline.state_of("f1")         # מצב המשימה
```

הוא דק בכוונה: כל החלטה נשארת אצל הרכיב שמחזיק אותה. מה שהוא כן מחזיק
הוא סדר הצעדים ומה קורה כשאחד מהם נכשל - קריאת מודל שנופלת או חורגת
מזמן נרשמת מול החלון שלה והעיבוד ממשיך. המשפטים כבר שמורים (רכיב 2 רץ
לפני התור), וצינור שהיה נעצר בחלון הראשון שנכשל היה מאבד כל משפט מאוחר
יותר של כל טיסה אחרת.

## רכיב 7 — מאגר אירועים ומצב המשימה (שלב 7)

מה שרכיב 6 קובע, כאן שורד אתחול. שלוש טבלאות, ושתיים מהן שונות
מהשלישית בדיוק באותו אופן שבו עובדה שונה ממסקנה:

| טבלה | מה היא | עדכון/מחיקה |
| --- | --- | --- |
| `events` | אירועים שזוהו | חסום במנוע |
| `state_changes` | כל שינוי מצב, עם ערך קודם וחדש | חסום במנוע |
| `entity_snapshots` | תמונת המצב הנוכחית | **מותר** - זה מטמון |

אירוע ושינוי מצב הם רישום של משהו שקרה, ודבר שקרה אינו מפסיק לקרות.
מעבר התיקון של שלב 11 אינו מתקן אותם - הוא *מוסיף* שורות מתויגות
`final` לצד אלה של זמן האמת, וזה בדיוק מה שמאפשר להשוות בין הגרסאות
אחר כך. תמונת המצב, לעומתם, ניתנת לבנייה מחדש מרצף השינויים, ולכן היא
הטבלה היחידה שמותר לדרוס - ומחיקתה אינה מאבדת דבר.

### שחזור לכל נקודת זמן

```python
store.rebuild_state("flight-01")                    # המצב הסופי
store.rebuild_state("flight-01", until=moment)      # "מה ידענו ב-06:03"
```

זהו קריטריון המעבר של השלב, והוא נבדק בצורתו החזקה: כל טיסת זהב רצה
דרך רכיבים 5-6 עם צילום מצב **אחרי כל אירוע**, ואז המאגר מתבקש לשחזר
את אותו רגע מרצף השינויים בלבד. ההתאמה היא 100% בכל נקודה.

אפשר לסמוך על זה כי מנהל המצב לעולם אינו משנה ערך במקום: כל ערך שהוחלף
נכתב לרשומת שינוי עם הערך הקודם והחדש. הלוג אינו תקציר של מה שקרה אלא
הרצף המלא, והרצתו קדימה אינה קירוב להרצה החיה - זה אותו חשבון באותו סדר.

הסדר הוא לפי `applied_at` ואז לפי מספר סידורי שנשמר בכתיבה. זמן לבדו
אינו מספיק: שני שינויים על אותו מאפיין יכולים לחלוק חותמת זמן, ושחזור
בסדר ההפוך נותן תשובה אחרת מזו שההרצה החיה נתנה.

### ייחוס לשני הכיוונים

`event_sources` היא טבלה נפרדת ולא JSON בתוך שורת האירוע, כי השאלה
נשאלת משני הצדדים:

```python
store.source_ids_of(event_id, flight_id)      # מאירוע → משפטים
store.events_from_message(message_id, flight) # ממשפט → אירועים
```

הכיוון השני הוא מה שיאפשר לקליינט לסמן משפט שהוליד אירוע, והוא דורש
אינדקס - שאילתה על JSON הייתה סריקה מלאה.

### בדיקות

35 בדיקות: append-only נבדק מול חיבור SQL ישיר (הערובה חייבת להחזיק גם
מול מי שעוקף את המודול), ייחוס דו-כיווני, הפרדה בין גרסת זמן אמת
לסופית, ושחזור מצב בכל נקודת בדיקה בשלוש טיסות הזהב.

## רכיב 8 — תקצירים ונקודות ציון (שלב 8)

שני פלטים מאותו חומר, לשני קוראים שונים.

**התקציר** הוא הקשר: תמונה עדכנית ומוגבלת בגודל שחוזרת ל-prompt של
החלון הבא, כדי שהמודל יֵדע מה כבר ידוע. תפקידו לאפשר למערכת לשכוח את
התמלול בלי לשכוח את הטיסה, ולכן הוא תחום בגודל ונכתב מחדש ולא מצטבר.

**נקודות הציון** הן לאדם: האירועים שבאמת חשובים, בסדר כרונולוגי, כל
אחד עדיין מצביע על המשפט שממנו בא. שום דבר לא מתומצת - נקודת ציון היא
אירוע אמיתי שנבחר, לא ניסוח חדש שלו.

### שני הקריטריונים מתנגשים, ומי מנצח

התכנית דורשת גם *"לא חורג מהגודל"* וגם *"100% מהישויות הפעילות"*. עם
מספיק מטרות פעילות אי אפשר לקיים את שניהם, ולכן ההכרעה כתובה מפורשות:
**הכיסוי מנצח, והחריגה מוצהרת בתוך התקציר עצמו.**

ההיגיון הוא שהתקלות אינן סימטריות. תקציר שחורג עולה טוקנים, וזה נראה
מיד. תקציר שמשמיט מטרה פעילה מאבד ידע על משהו שעדיין שם, ואין במערכת
דבר שיבחין בכך. לכן החיתוך הוא בסדר קבוע - תיאורים מתקצרים לפני ששמות
נעלמים, ורשימת הישויות היא הדבר האחרון שנשאר.

בפועל ההתנגשות נדירה: בנקודות הביקורת של טיסות הזהב יש 1-2 ישויות,
ושני הקריטריונים מתקיימים בנוחות.

### למה התקציר דטרמיניסטי כברירת מחדל

מודל שמתבקש "לתקצר בפחות מ-1200 תווים תוך אזכור כל ישות פעילה" בדרך
כלל ישמע, ולפעמים לא - ואין דרך לדעת איזו הרצה קיבלת. הרכבה שמבטיחה את
שניהם במבנה אפשר *לבדוק* שהיא מבטיחה אותם.

`LLMSummaryComposer` קיים למי שהניסוח חשוב לו יותר, והוא כן לגבי
העסקה: הוא בודק את הפלט של עצמו מול אותם שני תנאים, ונופל לאחור
לתקציר הדטרמיניסטי כשהמודל נכשל בהם. תקציר קריא פחות עדיף על תקציר
שמשמיט מטרה פעילה בלי שאיש ידע.

### מתי בכלל נכתב תקציר

מנהל המצב *מציע* טריגר, והמדיניות מחליטה. ההפרדה חשובה: רכיב 6 מציע
`significant_event` כמעט בכל חלון שבו משהו השתנה, וקבלה שלו כפשוטו
נותנת תקציר אחרי כמעט כל משפט - בדיוק מה שהתכנית אוסרת.

| טריגר | מתי |
| --- | --- |
| `mission_change` · `major_state_change` | מיד, בלי סף |
| `significant_event` | רק אחרי שהצטברו 8 אירועים |
| `threshold_exceeded` | 40 משפטים או 1500 טוקנים, גם בלי אף אירוע מהותי |

הרביעי חשוב במיוחד: טיסה ארוכה ושקטה צוברת הקשר שצריך לתקצר, גם אם לא
קרה בה דבר דרמטי.

### בדיקות

41 בדיקות, כולל שלושת קריטריוני המעבר: גודל, כיסוי 100% של הישויות
הפעילות, ואתחול באמצע טיסה שממשיך מאותו הקשר. אחת מהן היא המדידה
שהתכנית מבקשת - ספירת ההפעלות על טיסה שלמה, כדי לוודא שזה לא קורה
אחרי כל משפט.

## רכיב 9 — שירות שאילתות ותחקור (שלב 9)

`src/aura/query_service/` הוא הצד הקורא של המערכת, והרכיב הראשון שקיים
רק כדי לענות על שאלות ולא כדי להזיז את הטיסה קדימה. הוא קורא **אך ורק
מהמאגרים** - לא ממנהל מצב חי - ולכן הוא אינו צריך מודל, אינו צריך רשת,
ואפשר לבדוק אותו מול מסד שנטען מפיקסצ'רים בלבד, כפי שהתכנית מבקשת.

חמש השאילתות שהתכנית מונה:

| שאילתה | מה מחזירה |
| --- | --- |
| `current_state` | מצב המשימה עכשיו |
| `state_at(at)` | מצב המשימה כפי שהיה בנקודת זמן בעבר |
| `timeline(filter)` | ציר זמן של אירועים, מסונן |
| `sources_of(event)` | מאירוע -> משפטי התמלול שממנו נגזר |
| `summary(at)` | התקציר שהיה בתוקף באותו רגע |

ולצידן `events_from_sentence` (הכיוון ההפוך), `summary_history`,
`sentences_of_flight` ו-`version_diff`.

### קריאה מהמאגר ולא מהרכיב החי

זה מה שהופך את "מה היה המצב ב-06:20" לשאלה שאפשר לענות עליה בכלל: מנהל
מצב חי מחזיק מצב אחד, ההווה, ואי אפשר לשאול אותו על רגע שחלף. בנוסף,
שאילתה אינה מתחרה על אותו אובייקט עם הקליטה, ושירות שעלה מחדש עונה בדיוק
כמו זה שלפניו.

### זמן הוא זמן האמירה, לא זמן העיבוד

כל חותמת זמן שנכנסת לשאילתה או יוצאת ממנה היא **מתי המשפט נאמר**.
המאגרים חלוקים בנקודה הזו: `StateChange.applied_at` הוא כבר זמן אמירה,
אבל `Event.created_at` הוא הרגע שהוולידטור בנה את האירוע - ובטיסה
שמנותחת בדיעבד כל האירועים נבנים באותה שנייה. סינון לפי טווח זמן על
השדה ההוא היה מחזיר הכול או כלום, ולכן השירות פותר זמני אמירה מהמאגר
הגולמי (`timestamps_for_flight`) ומסנן לפיהם.

זו אותה תקלה שנמצאה בנקודות הציון בשלב 8, והפעם היא נמנעה מראש ומכוסה
בבדיקה: אירועים שעובדו בסדר הפוך לסדר האמירה חוזרים בסדר האמירה.

### מודלי קריאה נפרדים מהחוזים השמורים

קריטריון המעבר דורש "ממשק פנימי שאינו חושף מבנים של מנוע ה-LLM או של
מנגנון העדכון", ולכן שאילתה אינה מחזירה `Event` ואינה מחזירה
`StateChange` - אלא מודלי קריאה משלה (`models.py`). שני שדות נשארים
בחוץ בכוונה:

- **`window_id`** הוא תוצר של כללי הקיבוץ של רכיב 3, לא עובדה על הטיסה.
- **`confidence`** הוא מספר שהמודל פלט. תצוגתו כ-"0.82" מבטיחה דיוק
  שלא נמדד, ולכן מה שמוחזר הוא **רמת הוודאות** - אותה שלישייה
  (`verified` / `reported` / `uncertain`) שמצב המשימה עצמו רושם, מאותם
  ספים ממש. המיפוי חולץ ל-`certainty_for` כדי שלא יהיו שני עותקים
  שלו: אחרת שינוי סף אחד היה גורם לשאילתה לקרוא לאירוע "מאומת" בעוד
  שבמצב הוא נרשם כ"מדווח".

### סינון לפי ישות עובד דרך התווית, גם כשנתבקש מזהה

אירוע שמור נושא `EntityRef` שה-`id` שלו לרוב `None`: המודל נותן שם,
ומנהל המצב מקצה מזהה ואינו כותב אותו בחזרה לאירוע. סינון תמים לפי מזהה
היה מחזיר ריק דווקא לישויות שהטיסה חידשה - כלומר כמעט לכולן. השירות
פותר מזהה לתווית דרך מצב המשימה, ואז משווה תוויות מנורמלות. שתי הדרכים
מחזירות את אותם אירועים, וזה מפורש בבדיקה.

### בחירת גרסה: הסופית מנצחת, כשהיא קיימת

ברירת המחדל מהתכנית. הסיכון שהיא מסירה הוא תחקור שנעשה על טיוטת זמן
האמת ומגיע למסקנות ממידע שתוקן אחר כך. מעבר התיקון (שלב 11) טרם נכתב
ולכן היום ברירת המחדל נפתרת לגרסת זמן האמת - אבל קורא שאינו אומר דבר
יקבל את התשובה הטובה יותר ברגע שתהיה, בלי שיהיה צריך לשנות אותו אז.

שתי החלטות נוספות:

- **גרסה שנתבקשה במפורש מוחזרת גם אם היא ריקה.** "הגרסה הסופית של
  הטיסה הזו ריקה" היא תשובה; החלפתה בשקט בטיוטה הייתה מציגה טיוטה
  כתוצאה סופית.
- **בציר זמן שפרוש על כמה טיסות הגרסה נבחרת לכל טיסה בנפרד**, כי מעבר
  התיקון רץ בסוף כל טיסה בנפרד - וגרסה אחת לכולן הייתה מחזירה טיוטה
  לטיסה שכבר תוקנה.

הגרסה נבחרת ממאגר **האירועים** ולא מהתקצירים, כי האירועים הם החומר
והתקצירים נגזרים מהם. מכאן נובע חוזה כלפי שלב 11: טיסה שיש לה אירועים
סופיים אבל תקציר רק בגרסת זמן האמת מחזירה **"אין תקציר"**, ולא נופלת
לאחור לטיוטה - הצגת תקציר זמן אמת לצד אירועים סופיים היא בדיוק הבלבול
שסימון הגרסאות נועד למנוע. כלומר מעבר התיקון חייב לכתוב גם תקציר סופי,
לא רק אירועים סופיים. יש בדיקה שמקבעת את זה.

`version_diff` מסווג מה המעבר עשה (אושר / תוקן / נוסף / בוטל) לפי
הקישור שהגרסה הסופית נושאת בעצמה, ולא לפי השוואת טקסטים. הוא מבדיל בין
**ביטול** לבין **שתיקה**: אירוע זמן אמת שהגרסה הסופית אינה מזכירה כלל
מדווח כ-`unmatched` ולא כ"בוטל", כי סיווגו כבוטל היה שם בפי מעבר התיקון
טענה שלא טען. השאילתה נבדקת כבר עכשיו מול גרסה סופית שנבנתה ביד, כדי
שלא יישאר מה להוסיף בשכבת הקריאה בשלב 11.

### זמן תגובה - נמדד, לא מונח

התכנית מציבה "p95 < 500ms לטיסה בודדת" ומסמנת את המספר "לאישור".
`tests/test_query_performance.py` בודק את התקציב *וגם* מדפיס את מה
שנמדד, על טיסה של 3,000 משפטים (כ-3.3 שעות קשר רצוף) ו-600 אירועים:

| שאילתה | p95 |
| --- | --- |
| ציר זמן מלא | ~14ms |
| ציר זמן מסונן (סוג / ישות / טווח) | ~12-15ms |
| מצב נוכחי | ~2ms |
| מצב בנקודת זמן בעבר | ~2-6ms |
| מאירוע לתמלול | < 1ms |
| השוואת גרסאות | ~10ms |

כלומר התקציב גדול פי 25 לפחות ממה שנדרש. מדידה על טיסה פי ארבע ארוכה
(12,000 משפטים, 2,400 אירועים) נותנת ~72ms - גידול כמעט לינארי, עם
מרווח גדול.

**מה שהמדידה הכריעה:** השאילתה טוענת את זמני האמירה של הטיסה בכל
קריאה, בלי מטמון. מטמון נראה הכרחי לפני שנמדד והתברר כמיותר - הוא היה
קונה שבריר בלתי נראה מהתקציב בתמורה לנתון מתיישן בטיסה חיה, שבה משפטים
ממשיכים להגיע. לכן אין מטמון.

### זמן בלי אזור זמן נדחה, ולא מנוחש

זו הייתה התקלה האמיתית היחידה שנשארה בשלב הזה אחרי שהכול עבד. אותה
טעות - `datetime` בלי `tzinfo` - התנהגה בשלוש דרכים שונות:

| שאילתה | מה קרה |
| --- | --- |
| `state_at` | **החזירה מצב שגוי בשקט.** `astimezone(UTC)` על זמן חסר אזור מניח את שעת *המכונה*, ולכן נקודת החיתוך זזה לפי ההיסט של השרת |
| `timeline` | `TypeError` מתוך המיון |
| `summary` | `TypeError` מתוך ההשוואה |

הראשונה היא הגרועה: תשובה בטוחה-למראה על שאלה אחרת מזו שנשאלה.

הניחוש המתבקש הוא להניח UTC, כי כל מה שהמערכת שומרת הוא UTC וההנחה
הייתה נכונה כמעט תמיד. הוא נדחה בגלל מה ש"כמעט" עולה כאן: קורא
ב-UTC+2 שמבקש את המצב ב-06:20 מקומי היה רואה את 08:20 של הטיסה - רגע
אמיתי, עם ישויות אמיתיות, ובלי שום דבר שירמז שהתשובה היא לשאלה אחרת.
בכלי שכל תפקידו לשחזר מה היה ידוע ברגע מסוים, תשובה שהיא בביטחון
שלוש שעות מהמקום אינה טובה מסירוב שאומר איך לתקן.

לכן `require_aware` נקרא בכל נקודת כניסה של זמן, ו-`NaiveDatetimeError`
יורש גם מ-`ValueError` כדי ששכבת ה-HTTP של שלב 10 תחזיר 400 ולא 500
בלי להכיר את היררכיית השגיאות של הרכיב. גבולות הטווח נבדקים ב-
`EventFilter.__post_init__` - במקום שבו הערך נכנס, ולא בשורה שמשווה
זמנים, כי הראשון הוא זה שצריך לתקן.
