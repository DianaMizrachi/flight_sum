# aura — מערכת תמלול, זיהוי אירועים וסיכום טיסה

מימוש לפי [flight-transcript-work-plan.md](./flight-transcript-work-plan.md).
התמלולים בעברית; ה-LLM קורא ומזהה אירועים בעברית, והסיכומים (רכיב 7/8)
מופקים בעברית.

**מצב נוכחי: שלבים 0-3 הושלמו** - תשתית, חוזים ונתוני בדיקה (שלב 0),
רכיב 1 (קליטת משפטים) עם נרמול, זיהוי כפילויות, dead-letter ותור פנימי
(שלב 1), רכיב 2 (מאגר התמלול הגולמי) - append-only עם שליפה לפי מזהה,
טיסה וטווח זמן (שלב 2), ורכיב 3 (בניית הקשר) - חלונות, היסטוריה
רלוונטית ותקציב טוקנים (שלב 3). שלבים 4-12 עדיין לא ממומשים - רק המבנה
(`src/aura/<component>/`) קיים כשלד ריק לכל אחד מהם, לפי מבנה הרכיבים
בתכנית.

## הרצה מקומית

### התקנה

```bash
unset PYTHONPATH                    # ראו ההערה למטה - נדרש במכונה הזו
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev,api]"         # api נדרש להרצת השרת והדשבורד
```

> הערה לסביבה הזו בלבד: יש משתנה סביבה `PYTHONPATH` גלובלי שמצביע על
> `/usr/lib/python3/dist-packages` ומתנגש עם venv (שובר ייבוא `pydantic`).
> יש להריץ `unset PYTHONPATH` לפני הפעלת ה-venv. זו תכונה של המחשב הזה,
> לא של הפרויקט.

### בדיקות

```bash
pytest                              # 295 בדיקות, ללא רשת וללא GPU
ruff check src tests scripts
```

הבדיקות מריצות מודל מדומה בלבד. אין צורך ב-ollama, ב-docker או ב-GPU.

### השירות והדשבורד

```bash
uvicorn aura.api:app --reload
```

| כתובת | מה יש שם |
| --- | --- |
| <http://localhost:8000/> | דשבורד מצב המערכת + העלאת קובץ תמלול |
| <http://localhost:8000/docs> | Swagger |
| <http://localhost:8000/redoc> | ReDoc |
| <http://localhost:8000/status> | מצב המערכת כ-JSON |

המאגר נוצר ב-`var/aura-raw.db`. `AURA_RAW_STORE_PATH` מחליף אותו, ו-
`:memory:` נותן הרצה חולפת:

```bash
AURA_RAW_STORE_PATH=:memory: uvicorn aura.api:app
```

דרך הדשבורד (גרירת קובץ), או משורת הפקודה:

### תשתית אופציונלית

`docker-compose.yml` מרים Postgres ו-Redis בלבד. אין בו שירות LLM
בכוונה - ראו ההערה בקובץ. שום דבר ממה שרץ כאן כרגע אינו תלוי בו:
המאגר הוא SQLite והתור הוא בזיכרון עד שיוחלפו בשלבים מתקדמים.

## רכיב 1 — קליטת משפטים (שלב 1)

```python
from aura.ingestion import IngestionService

service = IngestionService()
result = service.ingest({
    "id": "flight-01-m01",         # אם חסר - נגזר מה-hash
    "flight_id": "flight-01",
    "timestamp": "2026-09-01T06:00:00Z",
    "source": "operator",
    "channel": "command",
    "text": "בקרה, נץ אחת, הכל תקין.",
})
result.status        # accepted / duplicate / dead_letter
result.message       # Message מנורמל (קיים גם לכפילות, מסומן כ-duplicate)
service.queue.drain()    # ההודעות שהועברו לעיבוד אסינכרוני
service.dead_letters     # הודעות פגומות, עם סיבה והמקור הגולמי
```

| כלל | התנהגות |
| --- | --- |
| נרמול | NFC, הסרת תווי כיווניות/אפס-רוחב, כיווץ רווחים, זמן ל-UTC |
| שמירת המקור | טקסט שעבר נרמול נשמר במקביל ב-`metadata["raw_text"]` |
| כפילות | לפי `id` מהמקור; בהיעדרו לפי hash של טיסה+מקור+זמן+טקסט |
| הודעה פגומה | dead-letter עם `reason` (`missing_required_field`, `empty_text`, `invalid_timestamp`, `schema_invalid`) |
| הודעה באיחור | `timestamp` המקורי נשמר כפי שהוא; `ingested_at` מתעד את זמן הקליטה |

שני דברים נדחו במכוון לשלב שבו יהיה להם צורכן: התור (`MessageQueue`)
והאינדקס (`DedupIndex`) מוגדרים כ-Protocol עם מימוש בזיכרון בלבד - מימוש
מעל Redis ומעל מאגר התמלול הגולמי נכנס בשלבים 2-3, כשיהיה מי שקורא מהתור
ומי שמזהה כפילות אחרי אתחול באמצע טיסה.

## רכיב 2 — מאגר התמלול הגולמי (שלב 2)

```python
from aura.ingestion import IngestionService
from aura.raw_store import RawStoreDedupIndex, SQLiteRawTranscriptStore

store = SQLiteRawTranscriptStore("var/aura-raw.db")        # ":memory:" לבדיקות
service = IngestionService(store=store, dedup_index=RawStoreDedupIndex(store))
service.ingest({...})                      # נכתב למאגר *לפני* שהועבר לתור

store.get("flight-01-m04")                 # שליפה לפי מזהה
store.by_flight("flight-01")               # כל הטיסה, בסדר כרונולוגי
store.by_time_range("flight-01", start, end)   # טווח זמן בתוך טיסה (כולל גבולות)
store.flights(); store.count("flight-01")
```

| כלל | התנהגות |
| --- | --- |
| append-only | אין `update` ואין `delete` ב-API, **והמנוע עצמו חוסם אותם** |
| סדר כרונולוגי | מיון לפי ה-`timestamp` המקורי, כך שהודעה באיחור חוזרת למקומה |
| טקסט | נשמר ונשלף זהה בייט-בייט; הנוסח שלפני הנרמול נשאר ב-`metadata["raw_text"]` |
| כפילות | כתיבת מזהה קיים מעלה `DuplicateMessageError`; `append_many` היא הכול-או-כלום |
| הודעה פגומה | אינה נכתבת למאגר - היא אינה `Message` תקין; המקור הגולמי נשמר ברשומת ה-dead-letter |

**חסימת עדכון ומחיקה "לא רק בקוד".** ב-SQLite האכיפה היא בטריגרים
(`schema.sql`), כך שגם SQL ישר נדחה:

```python
store.execute_sql("UPDATE raw_messages SET text = 'שונה' WHERE id = 'flight-01-m04'")
# AppendOnlyViolationError: raw_messages is append-only: UPDATE is blocked
```

ב-Postgres (היעד ב-docker-compose) האכיפה היא בהרשאות + טריגר:

```bash
docker compose exec -T postgres psql -U aura -d aura \
  < src/aura/raw_store/migrations/001_raw_messages.postgres.sql
```

הטבלה נוצרת בבעלות role של מיגרציות, והשירות מתחבר ב-role שמקבל
`SELECT, INSERT` בלבד - ב-Postgres בעל טבלה שומר תמיד את הרשאותיו, ולכן
`REVOKE` ממנו אינו מספק. המיגרציה עצמה אינה מורצת ב-CI (אין שם מסד); מה
שנבדק אוטומטית הוא מימוש ה-SQLite, שבו רצות כל בדיקות השלב.

**האינדקס הנמשך לזיהוי כפילויות.** `RawStoreDedupIndex` מחליף את האינדקס
בזיכרון של שלב 1, ולכן שירות שעלה מחדש באמצע טיסה עוד מזהה הודעה שכבר
נקלטה (נבדק ב-`test_raw_store.py`, וגם מול שרת חי).

מה שעוד לא: הכתיבה למאגר נעשית סינכרונית בתוך הקליטה. הקריאה מהתור
(עיבוד אסינכרוני בפועל) נכנסת בשלב 3 עם בניית ההקשר.

## רכיב 3 — בניית הקשר (שלב 3)

```python
from aura.context_builder import ContextBuilder, InMemoryEventHistory, assemble_windows

windows = assemble_windows(store.by_flight("flight-01"))   # חלוקה לחלונות
builder = ContextBuilder(history=InMemoryEventHistory(known_events))
bundle = builder.build(windows[0], current_state=state, last_summary=summary)

bundle.messages              # החלון, כולל החפיפה מהחלון הקודם
bundle.relevant_history      # רק אירועי הישויות שמוזכרות בחלון
bundle.token_budget          # budget / used_estimate / history_items_dropped
```

זרימת זמן אמת, מול זרימת סוף טיסה:

| מצב | כלי | התנהגות בהודעה שמגיעה באיחור |
| --- | --- | --- |
| זמן אמת | `WindowAssembler.push()` / `QueueWindowPump` | אם החלון שלה נסגר - נרשמת ב-`orphans` ולא נדחפת לחלון לא נכון |
| סוף טיסה / שלב 11 | `assemble_windows()` | ממוין לפי החותמת המקורית לפני החלוקה, ולכן אין יתומים |

שלוש החלטות תכן שהתכנית משאירה פתוחות, ומסומנות ב-`config.py`:

- **`max_sentences` כולל את החפיפה** (ה-LLM רואה אותה), אבל
  **`max_duration_seconds` נמדד על משפטי החלון עצמו** - אחרת שתיקה ארוכה
  שנגררה מהחלון הקודם הייתה סוגרת מיד את החלון החדש.
- **הודעה באיחור אינה נדחפת לחלון הפתוח** (`include_late_messages=False`):
  עדיף לרשום אותה כיתומה ולתת למעבר התיקון של שלב 11 לטפל בה, מאשר
  לשבש את סדר המשפטים בזמן אמת.
- **התאמת הישויות מתעלמת ממילה שמשותפת לכמה תוויות**: "מטרה" מופיעה
  בתווית של כל מטרה ולכן אינה מזהה אף אחת מהן, בעוד "אלפא" מזהה. בלי
  הכלל הזה חלון שמזכיר את אלפא היה גורר גם את ההיסטוריה של בטא.

### מה שהמדידה מראה על ספי החלון

החלוקה לחלונות רצה על שלוש טיסות הזהב ועל `samples/flight_sim_01.txt`
(62 משפטים בסך הכול), בכמה הגדרות:

| `silence` | `max_duration` | סגירה בהחלפת דובר | חלונות | משפטים לחלון | טוקנים מרביים |
| --- | --- | --- | --- | --- | --- |
| **20 (ברירת המחדל)** | **90** | **כן** | **61** | **1.0** | 447 |
| 20 | 90 | לא | 50 | 1.2 | 502 |
| 60 | 180 | לא | 40 | 1.6 | 502 |
| 180 | 600 | לא | 27 | 2.3 | 654 |

שתי מסקנות:

1. **בברירת המחדל כל חלון הוא משפט אחד.** הרכיב עומד בדיוק בכללים
   שבתכנית, אבל בתעבורת קשר אמיתית התוצאה היא קריאת LLM לכל משפט - בדיוק
   מה שהמעבר לחלונות נועד לחסוך. הגורם הדומיננטי הוא סף השתיקה
   (46 מתוך 61 הסגירות), לא החלפת הדובר.
2. **תקציב הטוקנים אינו האילוץ.** גם בהגדרה הרחבה ביותר חבילה אחת מגיעה
   ל-654 טוקנים מתוך 4000, כך שה-PLACEHOLDER של 4000 מרווח - והאילוץ
   האמיתי הוא מספר המשפטים והזמן, לא התקציב.

ההמלצה: `silence_threshold_seconds=60`, `max_duration_seconds=180`,
`close_on_speaker_change=False` - אלו מקבצים חילוף דברים שלם לחלון אחד
במקום משפט בודד. הערה חשובה: טיסות הזהב דלילות (12-14 משפטים לטיסה),
ושאלת "נפח ההודעות הצפוי לטיסה" פתוחה בתכנית - כשיהיו נתונים אמיתיים
כדאי להריץ את המדידה הזו שוב. ברירות המחדל בקוד נשארו **כמו בתכנית**
עד להחלטה.

## דשבורד מצב המערכת

```bash
uvicorn aura.api:app --reload      # ואז http://localhost:8000/
```

דף אחד שמרכז את מה שעד כה היה פזור בין התכנית, ה-README וקובץ ה-SQLite:
אילו שלבים נבנו, אילו רכיבים חשופים ב-API, כמה משפטים וטיסות במאגר, מה
בתור, אילו הודעות נדחו ולמה, האם ollama זמין ואיזה מודל מותקן בו בפועל,
ומה ספי החלון שבתוקף בהרצה הזאת. מתרענן כל 5 שניות כברירת מחדל, וניתן
לכבות.

### העלאת תמלול מהמחשב

בראש הדשבורד יש אזור גרירה ובחירת קובץ: בוחרים קובץ תמלול, אופציונלית
מזהה טיסה, ולוחצים "העלה וקלוט". התוצאה מוצגת מיד - כמה נקלטו, כמה
כפילויות, וטבלה של השורות שנדחו עם **מספר השורה בקובץ** והסיבה.

הפורמט הוא זה שמתועד ב-`samples/flight_sim_01.txt`:

```
message_id | timestamp | source | channel | text
```

שורות `#` וריקות הן הערות. מזהה הטיסה אינו שדה בשורה אלא תכונה של
הקובץ: הוא נלקח מהנחיית `# flight_id: <id>` שבקובץ, או מהשדה בטופס -
והשדה גובר. בלי אף אחד מהם הקובץ נדחה כולו ב-400, כדי שלא ייקלטו 29
הודעות שכולן חסרות את אותו שדה.

אותו דבר משורת הפקודה:

```bash
curl -X POST -F "file=@samples/flight_sim_01.txt" http://localhost:8000/messages/upload
```

הקורא (`ingestion/text_format.py`) מקפיד על המבנה ומקל על התוכן: שורה
בלי חותמת זמן או בלי טקסט נשלחת לקליטה בכל זאת ומגיעה ל-dead-letter עם
סיבה, במקום להיעלם בקורא. זה מה ששומר על לוג ה-dead-letter כמקום היחיד
לחפש בו הודעה שלא נכנסה. שתי נקודות שבהן המימוש המובן-מאליו מאבד מידע:
הטקסט נחתך ב-`maxsplit=4` כדי שמשפט שמכיל `|` יישמר, והריווח *בתוך*
המשפט נשמר כי הנרמול הוא תפקידו של רכיב 1.

כל הודעה שנקלטת מקובץ מקבלת `metadata.source_file` ו-`metadata.source_line`,
כך שאירוע שיזוהה בהמשך ניתן לייחוס לא רק למשפט אלא לשורה שממנה נקלט.
קובץ שאינו UTF-8 נדחה במפורש ולא מנוחש - עברית ב-cp1255 הייתה מתפענחת
לג'יבריש סביר למראה במקום להיכשל.

הנתונים באים מ-`GET /status`, והדף הוא HTML+JS ללא תלויות וללא שלב בנייה
(`src/aura/api/static/index.html`), מוגש מהשירות עצמו.

שתי הבחנות שהדף שומר במפורש, כי בלעדיהן דף מצב מציג תמונה אופטימית
מהמצב בפועל:

- **"נבנה" מול "חשוף ב-API".** רכיבים 3 ו-4 ממומשים ונבדקים, אבל הם
  ספריות - אף אחד לא קורא להם ב-HTTP. הצינור המלא מתחבר בשלב 6.
- **מודל מוגדר מול מודל מותקן.** `LLMConfig.model` הוא מחרוזת בקובץ
  הגדרות; הדף שואל את ollama מה באמת מותקן ומה טעון בזיכרון, ומסמן
  באדום מודל מוגדר שאינו קיים.

ollama שלא נגיש אינו מפיל את הדף - זה מידע, לא תקלה. הזמן קצוב ל-2 שניות.

## רכיב 4 — מנוע ה-LLM (שלב 4)

חלון משפטים נכנס, ``LLMResult`` יוצא. ארבעה חלקים:

| קובץ | תפקיד |
| --- | --- |
| `prompt.py` | prompt בעברית שנבנה מהטקסונומיה. הוספת סוג אירוע ל-`event_types.yaml` משנה את ה-prompt בלי שינוי קוד. |
| `client.py` | `LLMClient` כ-Protocol, `OllamaClient` אמיתי, `MockLLMClient` לבדיקות, ו-`RecordingLLMClient` שמייצר fixtures מתשובות אמיתיות. |
| `engine.py` | מריץ, מפענח ומאמת סכמה. `window_id`, `llm_model` ו-`raw_response` בבעלות המנוע ולא בבעלות המודל. |
| `scoring.py` | חמישה מדדים נפרדים: זיהוי, ייחוס מקורות, פיצול, מלכודות וסוג שגוי. |

**הסכמה שנשלחת למודל צרה מ-`LLMResult` בכוונה.** `LLMResult` כולל
`llm_model` ו-`raw_response`, שהם מטא-דאטה של ההרצה. בפענוח מוגבל-סכמה
מודל *חייב* למלא כל שדה בסכמה, כלומר היה נאלץ לנחש את שמו של עצמו -
ולכן המודל מוגבל ל-`ModelEventsResponse` (רשימת אירועים בלבד) והמנוע
עוטף את התוצאה.

**הפענוח המוגבל הוא גם הסיבה שקריטריון ה-98% אינו מדד שמבדיל בין
מודלים.** `format` של ollama מקבל סכמת JSON מלאה, ולכן JSON פגום אינו
אפשרי לשום מודל. המדד שבאמת מבדיל הוא ייחוס המקורות (90%).

### שני פרופילי prompt, כמדידה ולא כהעדפה

`MINIMAL` מגדיר את המשימה, הקטלוג ומבנה הפלט. `GUARDED` מוסיף שבעה
כללים: ציטוט מקור, אישורים שאינם אירוע, שאלות, שלילה, הוראות מותנות,
דיווחי שגרה, ו"אל תמציא". ההרצה בשני הפרופילים מפרידה בין "המודל לא
הבין את העברית" לבין "המודל לא יישם כלל שנאמר לו במפורש" - שתי תקלות
שהתיקון שלהן שונה לגמרי. בפועל: 796 טוקנים ב-`MINIMAL` מול 1,120
ב-`GUARDED`, מול `num_ctx` של 8,192.

### הרצת ההשוואה

ollama רץ על המארח (לא בקומפוז - ראו ההערה ב-`docker-compose.yml`):

```bash
ollama pull hf.co/dicta-il/DictaLM-3.0-Nemotron-12B-Instruct-GGUF:Q4_K_M

python scripts/evaluate_llm.py \
    --model hf.co/dicta-il/DictaLM-3.0-Nemotron-12B-Instruct-GGUF:Q4_K_M \
    --model qwen3.6:27b \
    --profile minimal --profile guarded
```

הסקריפט מריץ גם את סט הזהב (`--suite golden`) לקו הבסיס של
Precision/Recall, ו-`--record DIR` שומר כל תשובה אמיתית כ-fixture.
ברירת המחדל של החלונות בסקריפט היא התצורה המומלצת ולא זו של התכנית,
כי בתצורת התכנית כל משפט הוא חלון נפרד - ואז המודל רואה אישור בלי
הדיווח שהוא מאשר, כך שמלכודת הספירה הכפולה הופכת לארטיפקט של החלונות
במקום למדידה של המודל. `--plan-defaults` מודד בדיוק את ההפרש הזה.

## מודל LLM מקומי — בחירה

החומרה הזמינה: NVIDIA RTX A4500 Laptop (**16GB VRAM**), 62GB RAM.
הגבלת ה-VRAM היא מה שמכריע בפועל:

| מודל | רישיון | Q4 | נכנס ל-16GB? |
| --- | --- | --- | --- |
| DictaLM-3.0-Nemotron-12B-Instruct | NVIDIA Open Model License | 7.5GB | כן, עם מרווח ל-KV cache |
| DictaLM-3.0-24B-Thinking | Apache 2.0 | ~14GB | בדוחק, כמעט בלי KV cache |
| Qwen3.6-27B | Apache 2.0 | ~24GB | לא |

לפי הדוח של דיקטה (arXiv:2602.02104), במחלקת ה-12-14B: בהבנת עברית
(Winograd) 73.74 מול 73.38 ל-Qwen3-14B - כלומר תיקו; בהפקת עברית
(סיכום) 33.27 מול 15.83. כלומר **Qwen מבין עברית דומה אבל מפיק עברית
גרוע בהרבה.** זה מפצל את צורכי המערכת: פלט שלב 4 הוא JSON עם סוגים
מקטלוג סגור ו-`source_ids`, כמעט בלי הפקת עברית; שלב 8 (תקצירים) ושלב
10 (סיכום הטיסה) מפיקים עברית לתחקור. המספרים הם של היצרן, ו-Qwen נמדד
במצב thinking - ראו ההסתייגות בדיון.

הרישיון של ה-12B אינו Apache, וסעיף ה-guardrails שבו ראוי לבדיקה משפטית
לפני פריסה.

**התוצאה הפוכה מההמלצה שקדמה למדידה.** Qwen3-14B עובר את שער שלב 4
ו-DictaLM-12B לא, והפער הגדול הוא דווקא במקומות שבהם ציפינו שמודל עברי
ינצח:

- **שלילה (eval-02 m04, "שלילי... אין לי קשר רצוף"):** Qwen זיהה
  `loss_of_contact` נכון. DictaLM *דילג* על המשפט ולא הפיק ממנו אירוע
  כלל - כלומר לא היפוך משמעות אלא החמצה.
- **אירוע על שני משפטים (eval-03 m01+m02):** Qwen ציטט את שניהם.
  DictaLM ציטט את m01 בלבד *ופיצל* את האירוע לשניים.
- **ספירה כפולה:** DictaLM הפיק אירוע על 4 מלכודות (אישורים, הוראה
  מותנית, וביצוע הוראה שכבר נספרה), Qwen על מלכודת אחת.

**מצב החשיבה הוא מה שמכריע, לא המודל בלבד.** אותו Qwen בלי חשיבה יורד
ל-78% ייחוס ונכשל בשער - הוא מתחיל לצטט יותר מדי (מכניס את m03 לאירוע
הקשר ואת m08 לשינוי המשימה), בדיוק תקלת הספירה הכפולה. במחיר: פי 2.6
בזמן (295s מול 113s).

**שבעת כללי ה-`GUARDED` קונים מעט מאוד.** אצל DictaLM 88% ייחוס בשני
הפרופילים, ומלכודת אחת פחות. אצל Qwen הייחוס זהה וה-Precision עולה
מ-83% ל-91%. התועלת היא ב-Precision ולא בייחוס, וכמובן שהתרחישים אינם
"נפתרים" בכך שהכללים נאמרים במפורש.

הסתייגות: 10 אירועים ו-10 מלכודות הם מדגם קטן מאוד - אירוע אחד הוא
10%. המספרים האלה מכריעים בין שני מודלים, ואינם קו בסיס תקף לשלב 12.

**הערה לשלב 6 - כיול הביטחון:** התכנית מסתמכת על "ספי ביטחון והבחנת
ודאות" בשלב 6, ולכן שווה להסתכל על מה שהמודלים החזירו בשדה `confidence`:

על אותו חלון לא החזירו פלט זהה - בהרצה אחת Qwen החזיר צורת ישויות
שגויה ב-eval-01 ובהרצה אחרת נכונה. עם 10 אירועים בלבד, הפרש של אירוע
אחד הוא 10%, ולכן ההכרעה כאן מבוססת על פער גדול ועקבי (80%/88% מול
100%/100%) ולא על ההפרשים הקטנים בטבלה. לקו בסיס לשלב 12 יידרשו כמה
הרצות לכל מודל ויותר תרחישים.
